# Контрольные вопросы — Лабораторная работа 1

## 1. Почему хэширование пароля с помощью алгоритмов вроде bcrypt предпочтительнее использования SHA-256?

SHA-256 — это **криптографическая хэш-функция общего назначения**, спроектированная для скорости и эффективности. При хэшировании паролей скорость является недостатком: чем быстрее вычисляется хэш, тем быстрее злоумышленник может перебирать пароли методом грубой силы (brute-force) или по радужным таблицам (rainbow tables) после утечки базы данных.

bcrypt, напротив, является **адаптивной функцией хэширования паролей** со следующими преимуществами:

- **Соль (salt)** — bcrypt автоматически генерирует случайную соль для каждого пароля, что делает радужные таблицы бесполезными. Даже одинаковые пароли разных пользователей будут иметь разные хэши.
- **Настраиваемая стоимость (cost factor)** — bcrypt имеет параметр "стоимости" (work factor), который определяет количество итераций. Его можно увеличивать по мере роста вычислительной мощности hardware, сохраняя стойкость к перебору на десятилетия вперёд.
- **Встроенная замедленность** — bcrypt намеренно медленный: одна операция занимает ~100–200 мс на современном CPU, что делает brute-force практически нереализуемым при достаточно высоком cost factor. SHA-256 на том же оборудовании вычисляется за микросекунды, что даёт злоумышленнику миллионы попыток в секунду.
- **Стойкость к GPU/ASIC** — алгоритм bcrypt требует значительного объёма памяти (4 KB), что делает его неэффективным для распараллеливания на GPU и FPGA, в отличие от SHA-256, который легко ускоряется аппаратно.

Таким образом, использование bcrypt вместо SHA-256 необходимо для защиты паролей от массового перебора в случае утечки базы данных.

## 2. В чем заключается основная разница между SAST и DAST-подходом к тестированию безопасности?

**SAST (Static Application Security Testing)** — статическое тестирование безопасности:

- **Когда выполняется:** на этапе разработки, до компиляции или сборки (shift-left).
- **Доступ:** белый ящик (white-box) — анализатор имеет доступ к исходному коду или байт-коду.
- **Что анализирует:** синтаксис, поток данных, поток управления, конфигурации, зависимости.
- **Что находит:** SQL-инъекции (через статический анализ потока данных), XSS, buffer overflow, insecure crypto, hardcoded secrets.
- **Примеры:** SpotBugs, SonarQube, Checkmarx, Fortify SCA.
- **Достоинства:** находит проблемы на ранних этапах, покрывает все пути выполнения (включая неочевидные), не требует запущенного приложения.
- **Недостатки:** ложные срабатывания (false positives), не находит runtime-уязвимости (например, проблемы конфигурации сервера, бизнес-логики).

**DAST (Dynamic Application Security Testing)** — динамическое тестирование безопасности:

- **Когда выполняется:** на запущенном приложении, часто на этапе staging/QA.
- **Доступ:** чёрный ящик (black-box) — анализатор не имеет доступа к исходному коду.
- **Что делает:** отправляет HTTP-запросы с вредоносными payload'ами и анализирует ответы.
- **Что находит:** XSS (отражённые/хранимые), SQLi (через фактическую эксплуатацию), CSRF, неправильные заголовки безопасности, раскрытие информации.
- **Примеры:** OWASP ZAP, Burp Suite, Acunetix.
- **Достоинства:** минимум ложных срабатываний, находит реально эксплуатируемые уязвимости, проверяет конфигурацию среды выполнения.
- **Недостатки:** ограничен покрытием запросов (не все пути выполнения), требует работающего приложения, не находит уязвимости в неиспользуемых участках кода.

**Ключевое различие:** SAST проверяет **код** на потенциальные уязвимости статически, не выполняя его. DAST проверяет **работающее приложение** динамически, отправляя запросы и анализируя ответы. Оптимальная стратегия — их комбинация.

## 3. Опишите механизм работы JWT-токена. Какая информация в нем содержится и как сервер проверяет его подлинность?

### Структура JWT

JWT (JSON Web Token) состоит из трёх частей, разделённых точками (`.`):

**Header** (заголовок) — содержит метаданные о токене:
```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```
- `alg` — алгоритм подписи (HS256, RS256, и т.д.)
- `typ` — тип токена (обычно "JWT")

**Payload** (полезная нагрузка) — содержит утверждения (claims):
```json
{
  "sub": "admin",
  "role": "ADMIN",
  "iat": 1747500000,
  "exp": 1747586400
}
```
Стандартные claims (registered claims):
- `sub` (subject) — идентификатор пользователя
- `iat` (issued at) — время выдачи
- `exp` (expiration) — время истечения
- `iss` (issuer) — эмитент токена

Пользовательские claims (custom claims):
- `role` — роль пользователя
- Любые другие данные, необходимые приложению

**Signature** (подпись) — вычисляется по формуле:
```
HMACSHA256(
  base64UrlEncode(header) + "." + base64UrlEncode(payload),
  secret
)
```

### Механизм работы (на примере лабораторной работы)

1. **Аутентификация:** Пользователь отправляет `POST /auth/login` с логином и паролем.
2. **Верификация:** Сервер проверяет credentials (BCrypt), создаёт payload с `sub` (username) и `role`, подписывает секретным ключом (HMAC-SHA256).
3. **Выдача:** Сервер возвращает JWT клиенту.
4. **Хранение:** Клиент хранит токен (localStorage/sessionStorage/cookie) и отправляет его в заголовке `Authorization: Bearer <token>` при каждом запросе к защищённым endpoint'ам.
5. **Верификация запроса:**
   - Middleware (`JwtAuthFilter`) извлекает токен из заголовка.
   - Парсит header и payload (base64 decode).
   - Вычисляет подпись заново, используя секретный ключ.
   - Сравнивает вычисленную подпись с подписью в токене.
   - Проверяет срок действия (`exp`).
6. **Доступ:** Если подпись валидна и токен не истёк, сервер доверяет claims и устанавливает `SecurityContext`.

### Почему это безопасно?

- **Целостность:** Подпись гарантирует, что данные не были изменены. Злоумышленник не может изменить `role: USER` на `role: ADMIN`, не зная секретного ключа.
- **Stateless:** Серверу не нужно хранить сессии в БД — вся информация уже в токене.
- **Истечение:** `exp` ограничивает время действия токена, снижая риск при утечке.

## 4. Какие риски возникают, если не проводить аудит сторонних библиотек (зависимостей) в проекте?

### Основные риски

**1. Известные уязвимости (known vulnerabilities)**
Библиотеки содержат CVE (Common Vulnerabilities and Exposures). Примеры:
- log4j (CVE-2021-44228) — RCE через логирование
- jackson-databind — множественные уязвимости десериализации
- Поддельные/вредоносные пакеты в репозиториях (typoglycemia-атаки)

**2. Transitive dependencies (транзитивные зависимости)**
Уязвимость может находиться не в прямой зависимости, а в библиотеке, которую использует ваша библиотека. Разработчик может даже не знать о её существовании.

**3. Лицензионные риски**
- GPL/Affero GPL может потребовать открытия исходного кода всего проекта.
- Некоторые лицензии запрещают коммерческое использование.
- Нарушение лицензий ведёт к судебным искам.

**4. Устаревшие версии (outdated dependencies)**
Старые версии не получают патчей безопасности. Чем дольше не обновляются зависимости, тем больше накапливается технический долг и тем сложнее мигрировать.

**5. Malicious packages (атаки на цепочку поставок)**
- Злоумышленники публикуют пакеты с похожими именами (typosquatting).
- Взламывают аккаунты мейнтейнеров легитимных пакетов.
- Добавляют вредоносный код в популярные библиотеки (как в случае с event-stream и ua-parser-js).

### Практические последствия

| Риск | Последствие |
|------|-------------|
| RCE через Log4Shell | Полный компрометация сервера |
| SQLi через уязвимый ORM | Утечка БД |
| XSS через старую версию jQuery | Кража сессий пользователей |
| DoS через уязвимый парсер | Отказ в обслуживании |
| Крипто-майнер в зависимости | Финансовые потери, замедление системы |

### Как защититься

- **SCA (Software Composition Analysis):** OWASP Dependency-Check, Snyk, Dependabot.
- **Автоматизация:** Проверка зависимостей при каждом CI/CD-прогоне.
- **Политика:** fail сборки при CVSS >= 7.0.
- **Мониторинг:** Подписка на уведомления о новых CVE для используемых библиотек.
- **Регулярное обновление:** Минимизировать количество зависимостей, своевременно обновлять их.
